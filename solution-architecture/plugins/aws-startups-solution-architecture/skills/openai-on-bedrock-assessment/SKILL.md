# Assess Migration

Give a practical, repository-grounded assessment and implementation plan for migrating active inference routes to OpenAI models on Amazon Bedrock. This workflow is **read-only**: do not edit source, tests, configuration, routing, IAM, or infrastructure, and do not perform live or paid inference.

An inactive provider does not constitute a migration: the in-scope inference routes must actually use the documented Bedrock endpoint family for the selected model. Keep application hosting unchanged for inference-only cutovers; assess the execution and state changes of a separately chosen managed-agent integration explicitly. Assess only model integration, its surrounding application features, approved request and inference Regions, data residency, relevant inference permissions, data controls, and the narrow deployment and credential path needed for actual cutover. Do not expand into compute migration, networking design, general IAM architecture, general cloud readiness, or broader infrastructure.

Follow the [migration playbook](../../references/openai-on-bedrock-migration-playbook.md). Architecture-only advice is valid; identify assumptions when source code is unavailable. When troubleshooting this plugin itself, distinguish the active installed plugin cache path and `.claude-plugin/plugin.json` manifest version from its editable source checkout; a source edit does not change the already loaded skill.

Apply the playbook's two-phase policy to every starting point: least-disruptive supported **traffic cutover** first, then **strongly recommend optional modernization** to the newest suitable supported OpenAI models with **Responses** or the selected **Bedrock Managed Agents powered by OpenAI** integration. Implement additional modernization only when included in the requested or agreed scope; a cutover alone can satisfy the requested migration. Preserve the existing framework through current-version configuration, a minimal compatible upgrade, or a lightweight adapter. Keep supported Chat Completions during initial cutover when it is the smallest change; never downgrade existing Responses. Skip completed steps and avoid artificial intermediate transitions. Recommend Managed Agents by default for an existing managed-agent platform, and only as an optional alternative for application-owned agents or frameworks. Respect explicit user scope and constraints; report cutover and modernization separately, including any deferred or blocked objective.

## Fresh documentation and target decision

On every assessment or review, use the configured documentation MCPs to refresh the OpenAI-on-Bedrock guide, AWS model catalog, current endpoint recommendation, regional and CRIS deployment options, and recent model releases. Run the AWS `current_awareness` query even when the existing model is still supported. For agentic workloads, also retrieve current managed-agent guidance. Check model-specific lifecycle terms, and look up state portability when existing sessions, model switching, or provider fallback are in scope. Reconcile current deployment evidence with documentation using the playbook. Follow the playbook's evidence gate, endpoint/deployment decision, and managed-agent suitability checks; do not reuse a previous assessment's support matrix as current evidence.

For each distinct phase, record the retrieval date, exact sources, current suitable model candidates, and the selected model × endpoint or managed service × API × deployment mode × request/inference Regions. Apply compatibility gates to each phase independently, and recheck state portability, credentials, routing, and controls at every transition. Compare in-Region, geographic CRIS, and global CRIS against the customer's requirements. Identify documented support separately from account access and missing evidence. A newer announcement can expose a stale catalog entry; resolve each missing compatibility dimension rather than declaring the model unavailable or assuming it works.

## Workflow

1. Inspect authorized entry points, UI default and selectable routes, request handlers, supervisors, sub-agent constructors, provider selection, and every client that actually performs inference. Inspect model and inference-profile identifiers, manifests, lockfiles, the exact installed and nested transitive SDK package tree, framework versions, client transport, service and endpoint family, API operation, request and inference Regions, authentication, application-managed credentials, and relevant tests or evaluation suites. Distinguish existing **Bedrock Runtime** (`bedrock-runtime`) integrations from the documented target surface, including **Bedrock Mantle** (`bedrock-mantle`) where required; an existing Bedrock client does not establish compatibility with every Bedrock-hosted model. Resolve the actual underlying model using trustworthy evidence: a deployment alias or inference profile is not necessarily a model identifier. If it cannot be resolved, report it as unknown. Distinguish active routes from examples, optional integrations, and unreachable code. When application-owned deployment artifacts are available, trace only the endpoint family, provider, model or inference profile, approved Regions, CI configuration, deployment hooks, generated environment, and actual identity or credential-resolution path needed for active inference, including secret references when used; otherwise leave deployed routing unverified. Identify whether the application owns orchestration or uses a managed-agent platform, including a framework that calls that platform. Record which cutover and modernization outcomes are already satisfied, and pre-existing defects separately.
2. Retrieve the **latest official OpenAI and AWS documentation** needed for the observed source and the selected target's model, endpoint family, host and API path, client or operation, approved request and inference Regions, optional inference profile, authentication or signing, required inference-specific IAM permissions, relevant feature or prompt-caching support, and data controls. Before making a material claim, call the configured OpenAI Developer Docs MCP `search_openai_docs` and `fetch_openai_doc` tools, and the AWS Knowledge MCP `search_documentation` tool, including the required `current_awareness` query for recent model and endpoint releases. When AWS search results are incomplete, stale, or conflicting, call `read_documentation` for the fresh canonical model or endpoint page before considering website fallback. Use an official website only when its relevant tool is unavailable or insufficient, and report the fallback. Read the freshly retrieved canonical, model-specific official page body and the current documentation for its actual endpoint family, API, integration, authentication, inference profiles, and applicable permissions; reconcile conflicting evidence before making a material claim. Search snippets, localized copies, cached extracts, generic Bedrock endpoint guides, and another model's invocation examples do not establish model-specific endpoint support. Consult official source-provider, SDK, framework, or adapter documentation matching the installed or proposed version when relevant. Never rely on remembered availability, fixed Region lists, endpoint URLs, API paths, constructors, IAM actions, or cached capability claims. Preserve support-matrix icons, checkmarks, and alignment.
3. For each active in-scope route, select both a **cutover target** and a **modernization target** using the playbook. Respect explicit model and scope constraints. For cutover, prefer a supported same or documented equivalent model when that reduces disruption; use a newer eligible model immediately when equally straightforward. For modernization, recommend the newest suitable supported OpenAI model for the chosen Responses or Managed Agents integration, including when the workload already uses Bedrock. Verify the complete model, endpoint or service, API, client, authentication, deployment-mode, and Region combination separately for each target. Model availability elsewhere on Bedrock or the direct OpenAI API does not establish support for this combination. Unless the customer specifies another order, rank suitable candidates by **accuracy and intelligence first, latency second, and cost third**. Use the existing workload evaluation suite to justify a changed model; if representative evidence is missing, describe the checks and label the recommendation **provisional**. Explain an explicit constraint or blocker that prevents the default destination without silently treating an older model as fully modernized. Do not recommend open-source or open-weight models as targets. Select approved request and inference Regions dynamically; verify every profile destination against residency requirements, and never infer geography from timezone, locale, repository ownership, or source-provider location.
4. Choose the smallest documented integration **for each phase**:
   - **Existing Responses:** preserve the API; find a supported model/endpoint combination or report a blocker rather than downgrade to Chat Completions.
   - **Chat Completions:** retain it for the initial Bedrock switch when supported and least disruptive, then strongly recommend optional Responses modernization underneath the existing application contract. If it cannot support cutover, plan the smallest supported direct transition without an artificial intermediate API.
   - **Already on Bedrock:** cutover is satisfied only when the route already invokes an eligible OpenAI model there. A non-OpenAI Bedrock model still requires an OpenAI-model transition as part of cutover. Verify actual routing, skip only satisfied work, and strongly recommend any remaining optional model/API/service modernization. An existing Runtime or Mantle client still needs compatibility checks for the new target; change the transport when required, preserving unrelated routes.
   - **Installed frameworks**, including Microsoft agent frameworks: preserve the current framework in both phases through documented configuration/current-version support, then a minimal compatible upgrade, then a lightweight adapter or custom provider. Verify the API emitted underneath the framework; preserve orchestration, tools, streaming, state, and application interfaces.
   - **Application-owned agents or frameworks:** default to framework-preserving Responses; suggest Bedrock Managed Agents powered by OpenAI only as an optional alternative that addresses a concrete need.
   - **Existing managed-agent platform:** default to recommending Bedrock Managed Agents powered by OpenAI, subject to fresh service-specific access, model, Region, feature, state, and control evidence. Preserve any caller framework where possible. Consider a supported inference switch within the source platform first when simpler; otherwise assess direct service migration without forcing a temporary application-owned loop. If unsuitable, explain blockers and supported alternatives, including any gap from the default destination. Distinguish AgentCore options and Agents Classic from this service.
     Base each decision on current OpenAI, AWS, and version-matched framework evidence. Initial and final architectures may differ. If the least disruptive supported transition reaches the final target directly, plan one change with both outcomes verified. Never infer a client, endpoint, path, identifier, authentication mechanism, or inference permission from another model or service.
5. Build a concise **feature parity matrix** for only the capabilities the application actually uses or the user explicitly asks about. For each distinct phase, consult the current official documentation for the exact selected model, endpoint family or managed service, API, approved Regions, and applicable inference profile, then classify each capability as supported unchanged, supported with adaptation, unsupported but replaceable, blocking, or unverified. Check relevant hosted versus application-managed tools, function calling, streaming, structured output, modalities, state, persistence, prompt caching, and related controls only when relevant. Do not generalize caching, cache behavior, model comparisons, or other features across Bedrock endpoint families, APIs, models, Regions, or inference profiles without current model-specific support. For stateless `store: false` Responses tool loops, use the `reasoning.encrypted_content` include option when current documentation requires it; replay reasoning, the original `function_call`, and matching `function_call_output` as ordered top-level Responses input items without `previous_response_id`. Inspect server-sent events (SSE), `call_id`, parallel calls keyed by `output_index`, stale text deltas, model-specific context windows, and implicit sampling defaults where relevant. Verify the documented request and inference Regions, data residency, and effective retention requirements, including **zero data retention (ZDR)** where applicable. A request-level storage setting does not establish effective retention; distinguish documentation, configuration, and account evidence.
6. Identify the files and ordered changes for **cutover, its verification checkpoint, then recommended optional modernization and its verification**. Mark whether modernization is selected, recommended but not selected, or deferred; do not treat it as required for a cutover-only request. Keep the stages and rollback points separable when different changes are needed. Preserve the existing authentication and credential-delivery mechanism where documented support permits it; plan only necessary changes for the observed runtime, following the playbook. Container secret references and CI are applicable only when used by the deployment. Include local deployment, CI, dependencies, and secure credential delivery only where required by either authorized phase; preserve application behavior and retained integrations. Give readiness and effort separately for both phases, exact existing validation commands, and current official links. A blocked modernization branch does not block an independently supported cutover. Return the standardized assessment below; keep each section concise and do not replace individual repository reports with a comparison table.

## Assessment report

Use these headings in the same order for every repository.

### Readiness and migration effort

For **Traffic cutover** and **Modernization** separately, report **Readiness: READY | CONDITIONAL | BLOCKED** and **Estimated effort: LOW | MEDIUM | HIGH** for remaining work. State when a stage is already satisfied, recommended but not selected, or explicitly deferred by the user. Explain each classification briefly; a ready initial cutover does not make the final destination ready.

- `READY`: the required model, endpoint family, API, client, approved request and inference Regions, applicable inference profile, authentication, used features, and data controls are supported by current evidence, with no identified blocker.
- `CONDITIONAL`: required endpoint or API compatibility, model evaluation, approved request or inference Region, profile destination, authentication or inference permission, effective retention setting, or account prerequisite remains unverified.
- `BLOCKED`: no eligible model and endpoint combination exists within approved Regions, an inference profile violates required data residency, a required feature or data control cannot be preserved, or no candidate meets the established evaluation criteria.
- `LOW`: an existing supported API or provider integration requires mainly client, model, or configuration changes, including a Chat Completions cutover that retains its API.
- `MEDIUM`: direct Chat Completions-to-Responses translation, a framework upgrade, or a lightweight adapter is required.
- `HIGH`: agent-framework replacement, multiple active routes, or replacement of an essential application feature is required.

Classify each phase on its own work; do not charge a later API translation to a configuration-only cutover. These are migration-scoped classifications, not claims about general cloud or production readiness. Report evidence using the playbook's separate local/live status rules.

### Current workload

Explain the workload, who owns agent execution and state (application or managed platform), already-satisfied stages, each active inference route, actual underlying model, current provider and endpoint family, request API, model or inference profile, exact installed and nested SDK or framework versions, bound client and transport, request and inference Regions, authentication, application-managed credential mechanism, relevant evaluation suite, and model-adjacent features. Explicitly distinguish an existing **Bedrock Runtime** source integration from a **Bedrock Mantle** or other documented target integration. Identify the UI default, selectable alternatives, and clients bypassing a shared provider factory. Clearly distinguish unresolved deployment aliases, profile destinations, and unverified deployed routing. Do not assess unrelated compute, networking, general identity architecture, or infrastructure.

### Recommended Bedrock target

Show the **cutover target** and **modernization target** side by side, or state that they coincide. For each, identify the recommended OpenAI model, selected managed service when applicable, documented **endpoint family** such as **Bedrock Runtime** or **Bedrock Mantle**, exact documented endpoint host and API path when established, selected SDK client and API operation, endpoint-specific model or inference-profile identifier, approved request Region, every applicable inference destination Region, documented profile routing and data-residency compatibility, required authentication or signing, and relevant inference-specific IAM permission prerequisites. Derive these values from the live canonical documentation rather than fixed examples; clearly mark unavailable details as unverified. Respect an explicitly selected model. Identify the newest suitable supported modernization candidate even when retaining an equivalent model for initial cutover or assessing a workload already on Bedrock. Explain service-specific model availability and any explicit user constraint that changes the recommended destination. State the selected in-Region, geographic CRIS, or global CRIS mode and why it meets the customer constraints; show a regional alternative when a newer model requires ineligible routing. Record source retrieval dates. Cite the current official OpenAI and AWS documentation supporting material target claims.

### Model selection rationale

Identify the current model for each route and whether its documented equivalent supports the selected endpoint family, API, inference profile, and approved request and inference Regions. Explain any equivalent retained temporarily for cutover and justify the newest suitable supported modernization candidate using **accuracy and intelligence**, then **latency**, then **cost**, unless the customer explicitly specifies another order. Include migration effort, endpoint differences, prompt-caching behavior, and other concrete tradeoffs only when relevant and supported by current documentation. Identify the existing **evaluation suite**, results, and acceptance criteria supporting the recommendation; mark the recommendation **provisional** when representative evaluation evidence is missing. Never invent model-quality parity, feature support, pricing, or measured performance.

### Integration decision

For each phase, state the endpoint or service, client, transport, API, identifier, approved request and inference Regions, authentication, and inference permissions. Identify the branch: preserve Responses, retain Chat Completions initially then strongly recommend optional Responses modernization, implementing it only when selected, change Bedrock endpoint, configure/upgrade/adapt the existing framework, or migrate an existing managed-agent platform. Show the current-version configuration → minimal upgrade → lightweight adapter decision in both phases. Default application-owned agents to Responses and existing managed-agent platforms to Bedrock Managed Agents powered by OpenAI, subject to the playbook's suitability checks. Explain any optional service recommendation, necessary alternative, or framework replacement separately. Cite version-matched documentation and state the application behavior preserved.

### Migration approach

Provide two ordered phases: the least-disruptive supported **traffic cutover** and its verification checkpoint, followed by strongly recommended, optional **model/API/service modernization** and verification. Identify which work is in scope and which is a recommendation. Include only necessary endpoint, model/profile, framework, authentication, feature, state-portability, credential, deployment/CI, residency, and retention changes for each phase. Preserve retained routes and hosting for inference-only changes. Explain selected managed-service execution and state changes explicitly. Keep stages and rollback points separable when needed, and specify the same order for any later authorized live rollout. Skip already-satisfied work; justify a direct transition if it is the smallest supported route. State that modernization is optional but strongly recommended; distinguish it from unrelated improvements, and report blockers or user deferrals without invalidating a supported cutover.

### Files to change

List each affected file, explain its specific change, and provide a clickable host-native immutable permalink for remotely hosted repositories, such as a GitHub commit permalink, or an absolute local file link for local repositories. Label affected files by phase. Include application configuration, dependencies, tests, deployment parameters, secret references, hooks, CI, and operator documentation only when they directly support cutover or modernization. Clearly state when an exact file cannot be established.

### Compatibility and blockers

Provide a **feature parity matrix** for each distinct phase with each used or explicitly requested feature, source endpoint and API behavior, current documented target model, endpoint family, API and inference-profile support, required adaptation, and status. Explicitly address supported model and endpoint combinations, authentication and narrow inference-specific IAM prerequisites, approved request and inference Regions, cross-Region profile destinations and data residency, relevant prompt caching, and applicable **zero data retention (ZDR)** or other **effective retention** controls. A request-level storage flag alone is not proof of effective retention. Distinguish a documented unsupported endpoint combination from an unverified compatibility claim; a currently supported alternative endpoint can be an adaptation rather than a blocker. Separate supported behavior, routine prerequisites, unverified account settings, genuine blockers, and pre-existing defects. Do not speculate about capabilities the workload does not use or broader compute, networking, identity, or infrastructure migrations.

### Validation

Give separate cutover and modernization checks using exact existing commands where available. Test the actual API used at each checkpoint; do not impose Responses-loop tests on an interim Chat Completions route. Include focused local and migration-specific acceptance checks proving that each intended active inference route uses the documented endpoint family, exact actual request host and API path, selected client, correct endpoint-specific OpenAI model or inference profile, approved request and inference Regions, safe authentication boundary, and preserved application behavior. Identify a negative check that rejects a **Bedrock Runtime** request for a model documented only on **Bedrock Mantle**, or the reverse when applicable, while preserving unrelated source routes. Where the application owns a stateless Responses tool loop and streaming is used, specify a two-request mocked SSE test: stream a function call (and encrypted reasoning when the selected model/API contract requires it), execute the local tool, then inspect the second `/responses` request for documented ordered input items, the original `function_call`, matching `function_call_output` and `call_id`, and safe stateless settings. For managed-agent routes, specify service-contract and application acceptance checks for model routing, tools, sessions, memory, and controls rather than recreating an internal Responses loop. For a changed model, identify the existing evaluation suite and quality acceptance criteria, or state what representative evidence is missing. Never claim commands, tests, account checks, live inference, or evaluations ran when they did not.

### Unverified assumptions

Include only unknowns relevant to the model migration. Missing account access does not prevent useful assessment or local implementation; live access, effective permissions, and quality parity remain unverified without applicable evidence.
