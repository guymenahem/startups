# OpenAI on Bedrock Migration

Assess the actual application, implement its supported cutover and any selected modernization in sequence, verify every intended active route at each checkpoint, and independently review both outcomes. Follow the [migration playbook](../../references/openai-on-bedrock-migration-playbook.md). Do not require generated artifacts, unnecessary framework replacements, or a broader infrastructure migration. When troubleshooting the plugin itself, identify the active installed plugin cache path and its `.claude-plugin/plugin.json` manifest version separately from the editable source checkout; changed source instructions are not active until the installed plugin is refreshed.

Apply the playbook's two-phase policy to every starting point: least-disruptive supported **traffic cutover** first, then **strongly recommend optional modernization** to the newest suitable supported OpenAI models with **Responses** or the selected **Bedrock Managed Agents powered by OpenAI** integration. Implement additional modernization only when included in the requested or agreed scope; a cutover alone can satisfy the requested migration. Preserve the existing framework through current-version configuration, a minimal compatible upgrade, or a lightweight adapter. Keep supported Chat Completions during initial cutover when it is the smallest change; never downgrade existing Responses. Skip completed steps and avoid artificial intermediate transitions. Recommend Managed Agents by default for an existing managed-agent platform, and only as an optional alternative for application-owned agents or frameworks. Respect explicit user scope and constraints; report cutover and modernization separately, including any deferred or blocked objective.

## Fresh documentation and target decision

On every assessment or review, use the configured documentation MCPs to refresh the OpenAI-on-Bedrock guide, AWS model catalog, current endpoint recommendation, regional and CRIS deployment options, and recent model releases. Run the AWS `current_awareness` query even when the existing model is still supported. For agentic workloads, also retrieve current managed-agent guidance. Check model-specific lifecycle terms, and look up state portability when existing sessions, model switching, or provider fallback are in scope. Reconcile current deployment evidence with documentation using the playbook. Follow the playbook's evidence gate, endpoint/deployment decision, and managed-agent suitability checks; do not reuse a previous assessment's support matrix as current evidence.

For each distinct phase, record the retrieval date, exact sources, current suitable model candidates, and the selected model × endpoint or managed service × API × deployment mode × request/inference Regions. Apply compatibility gates to each phase independently, and recheck state portability, credentials, routing, and controls at every transition. Compare in-Region, geographic CRIS, and global CRIS against the customer's requirements. Identify documented support separately from account access and missing evidence. A newer announcement can expose a stale catalog entry; resolve each missing compatibility dimension rather than declaring the model unavailable or assuming it works.

## Workflow

1. **Assess the current implementation without changing files.** Trace the UI default, selectable orchestrators, request handlers, supervisors, sub-agent constructors, and every active in-scope inference client. Inspect its actual provider, underlying model, endpoint family, API operation, bound transport, hostname, request path, configuration, lockfiles, exact installed and nested transitive SDK or framework versions, relevant features, data controls, existing tests, and evaluation suite. Distinguish `bedrock-runtime` from `bedrock-mantle`, and distinguish Bedrock-native operations from OpenAI-compatible APIs; neither an existing Bedrock client nor a deployment alias proves the selected target is supported. Identify whether orchestration and state are application-owned or supplied by a managed-agent platform, including frameworks that call that platform. Record already-satisfied stages, preserve retained source routes, and record pre-existing defects. Before making a material claim, call the configured OpenAI Developer Docs MCP `search_openai_docs` and `fetch_openai_doc` tools, and the AWS Knowledge MCP `search_documentation` tool, including the required `current_awareness` query for recent model and endpoint releases. When AWS search results are incomplete, stale, or conflicting, call `read_documentation` for the fresh canonical model or endpoint page before considering website fallback. Use current official websites only when the relevant documentation tool is unavailable or insufficient, and report that fallback. Inspect the selected model's fresh canonical programmatic-access and endpoint-compatibility documentation, and resolve conflicting search snippets or generic recommendations before trusting material facts. Consult matching official framework, SDK, or source-provider documentation. Inspect application-owned deployment manifests, parameters, hooks, CI, runtime environment, and secret references only where needed to trace inference cutover; do not assess broader compute, networking, IAM, identity, or infrastructure architecture.
2. **Select the cutover and modernization targets.** For each route, follow the playbook's model-selection policy and respect explicit user scope and model constraints. A supported equivalent can minimize phase-1 disruption; the strongly recommended optional phase-2 destination is the newest suitable supported OpenAI model with Responses or the selected Bedrock Managed Agents integration. Refresh eligible candidates even for workloads already on Bedrock, and skip already-satisfied work. Resolve each target's model, endpoint or service, API, exact identifier/profile, client, authentication, permissions, deployment mode, request/inference Regions, used features, and controls together from current documentation. Do not infer compatibility from the Bedrock name or foundation-model availability. Rank suitable candidates by accuracy and intelligence, then latency, then cost unless the user specifies otherwise. Use existing authorized evaluation evidence for model changes or mark quality provisional. Report blockers per phase; a blocked final target must not block an independently supported cutover. Do not recommend open-source or open-weight targets.
3. **Choose the integration for each phase.** Preserve existing Responses; never downgrade to Chat Completions. Retain supported Chat Completions for the initial switch when least disruptive, then strongly recommend optional Responses modernization underneath the existing application contract and implement it when selected. For every framework, including Microsoft agent frameworks, preserve it using current-version configuration/client support, then a minimal compatible upgrade, then a lightweight adapter or custom provider. Verify the emitted API and preserve orchestration, tools, streaming, state, and application interfaces. For application-owned agents, default to Responses and offer Bedrock Managed Agents powered by OpenAI as an optional alternative. For an existing managed-agent platform, default to recommending that service, subject to the playbook's current service-specific suitability checks; preserve any caller framework. Use a supported source-platform inference switch as phase 1 when simpler, or a direct service transition when required. Do not force an intermediate self-managed loop or conflate AgentCore with Managed Agents. Explain blockers and alternatives when the default is unsuitable. Verify SDK-helper defaults and actual transport against each documented target; inspect feature parity, caching, credentials, state portability, routing, and effective retention at both transitions. Apply stateless Responses and managed-service contract requirements only to routes using those integrations.
4. **Present the phased assessment and plan.** Before editing, give **Readiness: READY | CONDITIONAL | BLOCKED** and **Estimated effort: LOW | MEDIUM | HIGH** separately for cutover and remaining modernization. Show both target combinations, framework decisions, affected routes/files, source links, blockers or user deferrals, ordered implementation steps, verification checkpoints, and rollback points. When one minimal supported change reaches both outcomes, explain that and avoid artificial intermediate work. Run a small existing authorized baseline check when practical. Apply evidence gates per phase: missing account access does not block documented local work, while a genuine compatibility blocker stops dependent changes.
5. **Implement phase 1: the least-disruptive supported local cutover.** Skip work already satisfied by verified existing routing. Change only in-scope code, configuration, deployment manifests and parameters, hooks, CI, dependencies, documentation, and tests needed for the supported OpenAI-on-Bedrock cutover. Retain the API/framework/model shape where supported; make only compatibility-required changes. Keep a separable checkpoint and rollback path when modernization will follow. Keep provider, endpoint family, API, model identifier or inference profile, and approved Region consistent across UI routes, local environment, deployment, and CI overrides. Preserve the application's existing authentication and credential-delivery mechanism where current documentation supports it for the selected endpoint, API, and runtime; make only necessary changes. Follow the playbook to trace the actual identity or credential source to the trusted inference client. Use container secret references only where applicable to the existing deployment; do not add containers, CI, or a stored secret solely to satisfy a credential pattern. Keep credentials out of source code, committed configuration, browser bundles, logs, deployment outputs, command arguments, unrelated subprocesses, and documentation MCP queries; check build contexts and generated files where applicable. Preserve effective retention, approved residency, application contracts, genuinely retained source credentials, unaffected routes, required safety controls, and customer isolation. Avoid unnecessary framework rewrites, dependencies, and speculative hardening.
6. **Verify the cutover checkpoint locally.** Run the smallest relevant existing local tests or checks; for Python projects, follow the existing `uv` workflow. Add or update a focused offline or mocked migration-specific check when existing tests do not prove each intended active route selects the documented Bedrock endpoint family, actual hostname, request path, API, target OpenAI model, exact endpoint-specific model identifier or inference profile, approved Region, documented authentication mechanism, credential boundary, and preserved application behavior. Where relevant configuration is available, also check documented inference permission actions and resources, profile routing destinations, and applicable data-residency constraints; do not claim offline evidence verifies an inaccessible live account. Reject an unsupported endpoint/model/API combination, an identifier valid only on another surface, and an SDK helper silently bound to the wrong endpoint. When the application owns a stateless Responses tool loop and streaming is used, cover a real two-request mocked SSE roundtrip: receive a streamed `function_call` and any encrypted reasoning required by the selected model/API contract, execute the application-managed tool, then assert that the second `/responses` request replays the documented ordered input items, original `function_call`, and matching `function_call_output` with its `call_id`, and preserves `store: false` without `previous_response_id`. Check parallel `output_index` handling and stale text deltas where relevant. For managed-agent routes, verify the documented service contract, actual Bedrock model routing, tools, session/memory boundaries, and controls; do not require an application-owned loop that the service replaces. A provider-construction test, passing source-provider test, or mocked response text alone does not establish cutover. Run existing model evaluation only when available and authorized; otherwise leave changed-model quality provisional. Fix in-scope regressions; report unrelated failures separately and stop only dependent work, with their root cause and minimal options. Record the tested checkpoint and evidence; local verification does not mean live traffic has shifted.
7. **Implement and verify phase 2 when selected.** Always strongly recommend the newest suitable supported model and Responses or a suitable Managed Agents integration, explaining benefits, effort, and tradeoffs. Implement additional modernization only when included in the requested or agreed scope; reuse existing authorization. Otherwise, finish the scoped cutover and report modernization as recommended but not selected or explicitly deferred. For selected modernization, proceed after the phase-1 local checkpoint. Follow the same configuration → minimal framework upgrade → lightweight adapter order, preserving application behavior and controls. Recheck the changed target's compatibility, state portability, credential scope, Regions, and service-specific features before editing. Reuse step 6's verification requirements for the final API/service and rerun checks affected by this phase, including relevant tool, streaming, and model evaluation checks. Keep changes and rollout/rollback steps separable when stages differ. Do not require a live deployment to continue authorized local work; specify that an eventual live rollout verifies traffic cutover before remaining modernization. If the first supported change already reaches the destination, verify both outcomes without duplicating work. If modernization is blocked, not selected, or explicitly deferred, complete independently supported cutover work and report that status separately. A scoped cutover can be complete without modernization; do not claim the recommended modernized state has been reached.
8. **Independently review both outcomes.** Request a fresh reviewer when available; otherwise perform a distinct fresh read-only review pass using `$aws-startups-solution-architecture:openai-on-bedrock-review`. Compare cutover and modernization implementation, sequencing, framework preservation, managed-platform recommendation, and checkpoint evidence against assessed routes, the selected model, endpoint family, API, identifier or inference profile, documented integration, relevant endpoint-specific feature parity, approved Region and residency, deployed configuration, credential containment, effective retention, evaluation evidence, and preserved source routes. Report prioritized `[P0]`, `[P1]`, or `[P2]` findings, or explicitly state that no actionable findings remain. Fix an authorized in-scope defect when needed, rerun relevant checks, and review the affected result again.
9. **Report the result.** Report **Traffic cutover** and **Modernization** separately per route, with readiness/effort, intermediate and final model/API/service, framework decisions, completed changes, exact validation commands/results, independent-review outcome, source links, and remaining blockers or user deferrals. Use the playbook's local/live status rules: local checks establish a locally verified implementation, not actual production traffic migration. State remaining account-access, effective-retention, residency, live-inference, and model-quality verification. Do not describe a retained interim model or Chat Completions route as completed modernization.

## Authorization

A request to migrate or implement authorizes relevant in-scope local cutover changes, ordinary focused local checks, and a distinct read-only final review. Additional modernization is optional and strongly recommended; implement it when requested or included in the agreed scope. Honor cutover-only scope, model constraints, and user deferrals; recommending an optional managed service does not require adopting it. A request only for advice remains read-only; use `$aws-startups-solution-architecture:openai-on-bedrock-assessment`. A standalone independent review belongs to `$aws-startups-solution-architecture:openai-on-bedrock-review` and remains read-only.

Do not run live or paid inference, weaken an existing control, apply IAM or infrastructure changes, export customer data, deploy, or change live production routing without authorization for that action. Editing an in-scope local deployment manifest does not authorize applying it. Missing AWS account access does not prevent a documented local implementation. Clearly distinguish passing local tests from verified account access, effective data controls, live inference, representative model quality, and production readiness.
