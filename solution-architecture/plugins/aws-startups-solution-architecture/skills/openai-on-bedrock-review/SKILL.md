# Review a Migration

Independently inspect the requested migration against the real application, assessment decisions, actual test evidence, and current official documentation. Follow the [migration playbook](../../references/openai-on-bedrock-migration-playbook.md). When reviewing this plugin itself, identify the active installed plugin cache path and its `.claude-plugin/plugin.json` manifest version, and distinguish them from the editable source checkout.

Review is **read-only**. Do not edit source, tests, configuration, IAM, infrastructure, or routing; do not submit comments, approve a change, or run live or paid inference. Inspect relevant existing test and evaluation results; run additional local checks only when the user separately requests that action. Review model integration, surrounding features, and the narrow deployment and credential path needed for inference cutover, not broader compute, networking, identity, IAM, infrastructure, or general cloud readiness.

Apply the playbook's two-phase policy to every starting point: least-disruptive supported **traffic cutover** first, then **strongly recommend optional modernization** to the newest suitable supported OpenAI models with **Responses** or the selected **Bedrock Managed Agents powered by OpenAI** integration. Implement additional modernization only when included in the requested or agreed scope; a cutover alone can satisfy the requested migration. Preserve the existing framework through current-version configuration, a minimal compatible upgrade, or a lightweight adapter. Keep supported Chat Completions during initial cutover when it is the smallest change; never downgrade existing Responses. Skip completed steps and avoid artificial intermediate transitions. Recommend Managed Agents by default for an existing managed-agent platform, and only as an optional alternative for application-owned agents or frameworks. Respect explicit user scope and constraints; report cutover and modernization separately, including any deferred or blocked objective.

## Fresh documentation and target decision

On every assessment or review, use the configured documentation MCPs to refresh the OpenAI-on-Bedrock guide, AWS model catalog, current endpoint recommendation, regional and CRIS deployment options, and recent model releases. Run the AWS `current_awareness` query even when the existing model is still supported. For agentic workloads, also retrieve current managed-agent guidance. Check model-specific lifecycle terms, and look up state portability when existing sessions, model switching, or provider fallback are in scope. Reconcile current deployment evidence with documentation using the playbook. Follow the playbook's evidence gate, endpoint/deployment decision, and managed-agent suitability checks; do not reuse a previous assessment's support matrix as current evidence.

For each distinct phase, record the retrieval date, exact sources, current suitable model candidates, and the selected model × endpoint or managed service × API × deployment mode × request/inference Regions. Apply compatibility gates to each phase independently, and recheck state portability, credentials, routing, and controls at every transition. Compare in-Region, geographic CRIS, and global CRIS against the customer's requirements. Identify documented support separately from account access and missing evidence. A newer announcement can expose a stale catalog entry; resolve each missing compatibility dimension rather than declaring the model unavailable or assuming it works.

## Workflow

1. Inspect the requested diff, implementation, or proposal alongside the preceding assessment, UI default and selectable routes, request handlers, supervisors, sub-agent constructors, client factories, and every actual inference client. Trace the underlying model or inference-profile identifier, endpoint family (`bedrock-runtime` or `bedrock-mantle`), resolved hostname and API path, client class and method, authentication strategy, bound transport, lockfiles, exact installed and nested transitive SDK or framework package versions, preserved source routes, used features, and existing test evidence. Follow the actual identity or credential-resolution path and documented inference permissions needed for active inference. Inspect application-owned deployment parameters, hooks, CI provider/model/Region/endpoint overrides, generated configuration, and secret references only where present and relevant. Identify the source architecture, including application-owned orchestration versus an existing managed-agent platform and any caller framework. Establish the intended scope and the intermediate and final targets, including already-satisfied or explicitly deferred stages. Do not infer a model from an unresolved deployment alias or endpoint compatibility from the Bedrock service name alone.
2. Fetch the **latest official OpenAI and AWS documentation** for the actual target model, approved Region, endpoint family, API, relevant feature parity matrix, inference authentication and authorization, and required data controls. Before raising a finding, call the configured OpenAI Developer Docs MCP `search_openai_docs` and `fetch_openai_doc` tools, and the AWS Knowledge MCP `search_documentation` tool, including the required `current_awareness` query for recent model and endpoint releases. When AWS search results are incomplete, stale, or conflicting, call `read_documentation` for the fresh canonical model or endpoint page before considering website fallback. Use an official website only when its relevant tool is unavailable or insufficient, and report that fallback. Read the fresh canonical, model-specific page body and relevant endpoint-specific documentation; reconcile conflicting publication dates, stale snapshots, API and Region availability, model or inference-profile identifiers, and feature claims before raising a finding. Check publication and update dates at claim level: an older canonical table may lag a newer official release. Follow new releases to model-specific endpoint and deployment evidence; an announcement alone cannot supply omitted compatibility details. Treat unresolved documentation freshness or conflicts as unverified, not as confirmed support or failure. Consult version-matched official SDK, framework, or source-provider documentation only when relevant. Do not substitute remembered availability, capabilities, endpoints, or account settings for current official evidence.
3. Confirm model selection and the documented endpoint-or-service × model × API × Region × required-feature combination at each distinct checkpoint for each active in-scope route. Verify the exact resolved hostname, API base path, client method, authentication scheme, and endpoint-specific model identifier or inference profile; do not assume that an identifier supported by one endpoint family works on another. Check the selected AWS Region, any geographic or global routing destinations, applicable inference-profile requirements, and required data residency against current official evidence. Confirm that the recommendation respects an explicitly selected target and considers current suitable candidates, including newer eligible models. Preserving an equivalent can be appropriate for initial cutover. Confirm a recommendation for the newest suitable supported modernization model with Responses or the selected Bedrock Managed Agents service, including when already on Bedrock. Respect explicit constraints and show any remaining gap; support on direct inference does not establish service-specific model availability. Unless the customer specifies another priority, assess accuracy and intelligence first, latency second, and cost third. Check whether a changed-model recommendation is justified by the existing evaluation suite; report unavailable representative evidence as provisional. If no suitable target is available, report a model-availability blocker. Do not recommend open-source or open-weight models as migration targets.
4. Check both phases against the source architecture and the playbook. Initial cutover should use the least-disruptive supported path, retaining Chat Completions when appropriate; existing Responses must not be downgraded. Strongly recommended modernization should target the newest suitable supported model and Responses underneath the existing framework or the selected Managed Agents integration. Check implementation only when modernization is selected; not adopting it must not fail an otherwise completed scoped cutover. Check current-version configuration → minimal compatible framework upgrade → lightweight adapter, including Microsoft frameworks; verify the emitted API and preserved orchestration, tools, streaming, state, and application interfaces. For application-owned agents, Responses is the default and Managed Agents optional. For an existing managed-agent platform, Bedrock Managed Agents powered by OpenAI is the default recommendation, subject to documented suitability and user constraints. Review any caller framework separately from the source service. Explain justified alternatives rather than requiring a temporary self-managed loop or forcing a service adoption. Check current service-specific lifecycle/access, model/API, Regions, identity, tools, state, memory, retention/deletion, and adoption effort. Do not conflate Managed Agents, AgentCore, and Agents Classic. Verify actual client/transport, dependencies, credentials, permissions, constructors, active routes, and retained integrations at both phases.
5. Check each phase's endpoint-, service-, and API-specific feature parity matrix, state portability, approved Region, required safety or privacy controls, and effective retention. For features the application actually uses, verify current documented support on the selected endpoint and API for prompt caching and cache configuration, server-side or application-managed tools, streaming, background execution, structured outputs, state management, projects, safety controls, and any other required behavior; do not transfer a capability from one endpoint family or API to another without current evidence. When relevant, confirm that **zero data retention (ZDR)** is supported by current official documentation and applicable configuration evidence; a request-level flag alone does not prove effective retention. For stateless `store: false` Responses tool loops, inspect the `reasoning.encrypted_content` include option when current documentation requires it, ordered top-level reasoning, the original `function_call`, matching `function_call_output` and `call_id`, absence of `previous_response_id`, server-sent events (SSE), parallel tool aggregation by `output_index`, stale text deltas, sampling defaults, and model-specific context windows where actually used. Confirm that the existing authentication and credential-delivery mechanism is preserved where supported by current documentation, with only necessary changes. Trace the actual identity or credential source to the trusted inference client using the playbook; validate resolution and refresh without assuming a stored secret, CI, or a container deployment. Check secret references, build exclusions, and deployment parameters only when used. Check source/configuration files, browser bundles, logs, outputs, command arguments, and unrelated subprocess/MCP exposure. Absence of containers or CI is not a defect when the runtime uses a supported authentication mechanism. Distinguish required hosted features from application-managed alternatives. Do not treat unused features, optional examples, undocumented restrictions, or stale search results as confirmed migration blockers.
6. Examine separate cutover and modernization checkpoint evidence, including whether the initial route was verified before remaining modernization changes, or one supported transition satisfied both outcomes. Assess the separable rollout/rollback plan when phases differ. Test expectations must match each phase's actual API; interim Chat Completions does not need a Responses-loop test. Examine whether migration-specific tests establish Bedrock routing for each intended active route, including target provider or client, OpenAI model, documented endpoint family and API, trusted credential boundary, and relevant application behavior. Look for existing offline endpoint-contract evidence that inspects the actual constructed request hostname, full API path, client method, wire-level model or inference-profile identifier, approved Region, authentication strategy, and documented IAM assumptions without exposing secrets or requiring live inference. For application-owned stateless Responses streaming tools, look for a two-request mocked SSE test that emits a streamed function call and any encrypted reasoning required by the selected model/API contract, executes the local tool, and inspects the second `/responses` request for the documented ordered input items, original `function_call`, matching `function_call_output` and `call_id`, and safe stateless settings. For a managed-agent route, inspect the documented service contract and evidence for actual Bedrock model routing, tools, state boundaries, and controls; do not require reconstruction of its internal model loop. A provider-construction test, passing source-provider test, mocked response text, or endpoint-agnostic client assertion alone is insufficient. Distinguish pre-existing defects from migration regressions and static review from existing local test results, account settings, authorized live inference, and representative changed-model evaluation.
7. Report **Traffic cutover** and **Modernization** separately per route, including **Readiness: READY | CONDITIONAL | BLOCKED**, **Estimated effort: LOW | MEDIUM | HIGH** for remaining work, model/API/service targets, and local/live verification status using the playbook. Identify remaining work, blockers, and explicit user deferrals. Then give concise, evidence-backed findings ordered by priority:

   - `[P0]`: broken behavior, a confirmed invalid active endpoint-family/model/API/model-or-profile-identifier combination, credential exposure, unsafe routing, data loss, or a violated required security, privacy, Region, retention, or safety control.
   - `[P1]`: a likely migration failure, unsupported or unverified endpoint, model, API, integration, required feature, Region, authentication, or IAM permission in the scoped implementation; an omitted active route or required behavior; a dependency conflict; missing required evaluation for an implemented model change or an unqualified quality claim; an omitted modernization recommendation or unsupported completion claim; or another important unverified claim. A clearly provisional optional recommendation does not require an executed model evaluation or implementation tests.
   - `[P2]`: an optional clarity or maintainability improvement that directly helps the requested migration.

Review the intended phase, not an invented completed end state: a supported interim older model or Chat Completions route is valid when labeled and paired with the remaining modernization plan. Modernization that is not selected, user-deferred, or blocked is a status to report, not automatically a defect in supported cutover work. Do not require optional modernization to approve a cutover-only migration. Flag missing plans, avoidable framework replacement, or false completion claims when they conflict with the agreed scope. For each finding, identify the relevant file or route, concrete impact, and the smallest practical fix. Do not present speculative risks as confirmed or require features the application does not use. If there are no actionable findings, say so and name meaningful remaining migration-scoped test, evaluation, effective-retention, account-access, or live-verification gaps. Include relevant official OpenAI and AWS documentation links for material recommendations.

If the user requests fixes, use `$aws-startups-solution-architecture:openai-on-bedrock-migration` with the newly authorized scope; do not implement changes during the review itself.
